## Done
- **Phase 0 — ATS mapping** (`tools/ats_probe.py`): 58 companies probed. 25 have a public API (21 Greenhouse, 4 Ashby) with 408 Israel jobs. Comeet (9 companies) deferred, ADR-002. 14 large companies have no public API (Workday or in-house).
- **Phase 1 — collection** (`jobfinder scan`): Greenhouse and Ashby sources, SQLite store with first_seen / last_seen / closed_at, boards in `data/sources.toml`. Acceptance check: 10 runs, 1,450 jobs, 0 duplicate keys, every job has a full description.
- **More boards (2026-10-28):** 9 more companies from a second probe run; 34 boards, ~1,600 open jobs (1,625 with alerts on 2026-10-28; the filter keeps 190). Little gain: board companies rarely post student / junior roles.
- **LinkedIn alerts source (2026-10-28, ADR-008)** (`jobfinder alerts`): reads LinkedIn job-alert emails from a dedicated Gmail mailbox used only for alerts (~2,000 alerts since 2025-04) over read-only IMAP. Credentials live only in `.env` (`ALERTS_EMAIL_ACCOUNT`, `ALERTS_EMAIL_APP_PASSWORD`, an app password). The parser handles English and Hebrew alerts (296/296 jobs on a 53-alert sample). Alert jobs have no description (`description_text=None`, DB schema v2) and are never closed. First import (14 days): 18 jobs, all pass the filter, mostly junior / graduate roles at companies without an API (NVIDIA, Mobileye, Intuit, Dell, Check Point).
- **Phase 2.1 — labeling tool** (`jobfinder label`): shows one job at a time; `y` / `n` with a required reason, `s` skip, `o` open, `b` back, `q` quit. Appends to `data/labels.jsonl` (gitignored, personal) with a full job snapshot. Seeded order (changed 2026-10-28): 30% email-alert jobs, 40% board jobs the pre-filter keeps, 20% Israel jobs the filter rejects, 10% outside Israel. Board jobs have almost no student / junior roles, so the old 70% Israel share risked too few "fit" labels to measure recall.
- **Alerts backfill (2026-10-28):** `jobfinder alerts --days 120` imported 442 more alert jobs (461 in all, 437 pass the filter). It takes ~10 minutes, one IMAP fetch per email.
- **Phase 2.3–2.4 — extractors** (`extraction/`, `jobfinder extract`): `Extractor` protocol returning `Extraction` (`years_required`, `onsite_days`, `is_student`, `location`, `stack`) plus token counts. `GeminiExtractor` (default `gemini-3.5-flash`, `responseJsonSchema`) and `OllamaExtractor` (default `qwen2.5:14b`, `format` schema) share one prompt and schema in `extraction/base.py`. `UrllibPoster` retries 429 / 503 after 5, 20, 60 s. First real run: Gemini 8/8 jobs in 87 s, ~840 input and ~570 output tokens per job (most of the output is thinking); Ollama `qwen2.5:14b` ~60 s for the first job (model load) and a longer, noisier stack list. Local models available: qwen2.5 14b / 32b, gemma2 9b / 27b, llama3.1 8b, gemma4.

**Matches page (2026-10-28):** `scoring.py` reads `priorities.txt` (TOML) and scores level 40 / field 30 / location 20 / office days 10, with hard rejections (too many years, unwanted field, too far) and three verdicts: match, maybe (level unknown), no. `jobfinder ui` serves the scored list on 127.0.0.1:8765. `jobfinder extract --all` reads every filter-kept job with a description into the cache (first run with Ollama `qwen2.5:14b`, ~173 jobs). On 2026-10-28 before extraction: 610 kept jobs, 64 match, 466 maybe, 80 no. The user asked for this page before the Telegram bot.

**Suggestions (2026-10-28):** 126 in `data/suggestions.jsonl`, 28 fit (31 added from entry-level alert titles; duplicates of the same company + title left out). `jobfinder label --target 126` reviews them all.

**Labeling screen (2026-10-30):** `jobfinder ui` now serves `/label`: one job at a time with the suggestion, buttons and keys (Enter accept, Y / N with a reason, S skip, B back, O open), progress against the 15 fit labels needed. It writes the same `data/labels.jsonl` as `jobfinder label`, in the same order (`sampling.review_queue`). The server now writes, so it checks the Host header and needs a per-run token to save. On 2026-10-30, 118 of the 126 suggested jobs were still open, so that is the review count; suggestions for closed jobs are not shown.

**First eval (2026-10-30):** the user answered 16 suggestions at `/label` (changed 1) and approved the other 110 as a batch, saved with `bulk_accepted`: 126 labels, 29 fit. Precision of match: 87% from titles alone, 87% with Gemini (it has read only 2 of these jobs, so this says nothing about it), 79% with Ollama (38 read, and it adds 3 wrong matches). Recall of match 90%, match or maybe 100%, student recall 100% (5/5). Treat these as optimistic: the labels came from the same CV and `priorities.txt` as the scoring, and many reasons are guesses from a title. Only 16 labels are individually answered, with 5 fit, so G1 and G2 are not proven yet. Wrong matches to look at: customer-facing titles (Solution Engineer, Forward Deployed), MLOps, a security analyst and a Biz Ops role.

**Scoring tuned (2026-10-30):** three code fixes in `scoring.py`: `years_required` 0 no longer proves an entry-level job (all 5 such non-entry postings stated no years, so 0 is what the model writes for "not stated"); a job with 0 field points is a maybe, never a match; a word before a loose hyphen now counts ("Student- Glil Yam"). `priorities.txt` gained reject words (biz ops, security analyst, SOC, MLOps, solution / solutions engineer, forward deployed, career path) and field words (SW, AI engineer, automation engineer). Live list: 71 matches became 49, 8 InfinityLabs "career path" jobs are now rejected on one guessed label. Eval on the 126 labels: precision 100% (27/27), match recall 93%, match or maybe 100%, student recall 100% (6/6). These numbers are on the labels the tuning was based on, so they do not prove the goals: judge the next new jobs instead.

**Blind check (2026-11-02):** only 10 jobs arrived after the tuning (1 match), too few to measure, so the check used the 23 live matches that had no label plus 2 unlabeled student jobs. `/label` now offers those first, with no suggestion shown, and `jobfinder eval --since 2026-11-02` reports them apart. Result with the live pipeline (Ollama where it read the job): precision 96% (22/23), or 94% (17/18) counting duplicates once, so G1 holds. Student jobs: of 3 unlabeled, 1 fit and shown, 2 not the user's field; every student title now open has a label, 7 of 7 fit ones shown, 6 of them bulk accepted, so G2 has little individual evidence. This check is easy for the scorer: 49 of the 50 live matches have "junior" or "student" in the title and no model answer behind them. The one match the model decided is the one mistake: Taboola Fraud Analyst, which asks "1-2 years"; the model correctly gave the minimum, 1, and the user judged it too senior. So G1 says little about the extractor, and comparing Gemini with Ollama would barely change the matches. What the model could change is hidden in the 373 maybes, which nobody has measured.

**Digest (2026-11-02, Phase 3, first step):** `jobfinder digest` (`digest.py`, `telegram.py`) selects jobs first seen in the last 7 days and never sent: up to 15, matches first, then up to 5 maybes with field points and at least 50 points. Same company + title is one item, across sources. A label of not fit silences a job. The field-points condition came from the first dry run: points alone sent Car Advocate and Office Admin. Sent jobs are in the `digest_sent` table (DB schema v4, backup of v3 in `data/jobs.v3-backup.db`). The first real digest went out on 2026-11-02 with 1 match and 4 maybes, and `scripts/daily.cmd` now sends it; a full run of the script ended with exit 0. An empty digest sends nothing, so a quiet day and a failed run look the same in Telegram: check the log's exit line.

**Digest buttons (2026-11-02):** each job is now its own message with Applied, Not relevant and Later (DB schema v5, table `digest_answers`, backup of v4 in `data/jobs.v4-backup.db`). `jobfinder digest` pulls presses with `getUpdates` before it selects jobs, so nothing stays running. Applied and Not relevant also append a label, so these reach `jobfinder eval`. Later brings a job back in the next digest, whatever its age. Only presses whose user and chat are `TELEGRAM_CHAT_ID` count. Checked on a real press on 2026-11-02: one Applied was read, saved and labeled.

## Known gaps
- Button presses are read only by the daily run, so a press shows nothing until the next run, and Telegram drops presses after 24 hours. Running `jobfinder digest` more often would shorten that, but it would also send new jobs at that moment.
- A job the user never answers is not shown again.
- The Telegram token was pasted into a chat on 2026-11-02. If it was not revoked in BotFather afterwards, revoke it and update `.env`.
- The daily run of 2026-11-01 started at 09:14 and logged nothing after its header, not even the exit line. Cause unknown: Task Scheduler history is off, and the system log shows only a shutdown at 12:33. The next run was fine, and the task has a 30-minute limit. Watch for a header with no `exit:` line.
- A posting asking "1-2 years" counts as 1, because `years_required` is the minimum. The user judged such a job too senior (Taboola Fraud Analyst). Telling them apart needs the top of the range from the extractor.
- The 373 maybes are unmeasured: a job with no "junior" in the title and no years stated stays a maybe, so the digest needs a rule for which maybes to show.
- Alert jobs never close (an alert lists only new jobs). Phase 3 must show only recently first-seen alert jobs, or expire them by age.
- Alert jobs have no description, so the extractor and scoring work from the title only for them.
- Only LinkedIn alerts are parsed. AllJobs / Drushim alerts need their own parser once the user subscribes them to the same mailbox.
- Only 2 student and 1 junior titles exist across the 25 boards: the eval set may get few "fit" labels, and the sources may not match a student / junior search. Raise with the user after labeling.
- The old repo `alexfunking/The_job_Finder` is public and contains `priorities.txt` (personal). Archiving does not hide it; making it private does.
- Closing and reopening jobs is verified only in unit tests; real behavior shows after days of daily scans (running since 2026-10-28, see `data/logs/daily.log`).
- The labeling order draws 70% from board jobs, which have almost no student / junior roles, while the alert jobs are nearly all junior. Consider putting alert jobs and filter-kept jobs first, and backfilling alerts beyond 14 days (~2,000 since 2025-04), so the eval set has enough "fit" labels to measure G2.
- The same job can arrive from a board and from a LinkedIn alert under different keys: Phase 3 grouping must work across sources.
- Cost of the Haiku extractor is a rough estimate (under $1 for the whole DB); measure on the eval set.
- Workday terms of use not checked yet (after the MVP, ADR-007).
